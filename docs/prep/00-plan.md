## 1. 준비 단계에서 지킬 것

1. **작업 브랜치는 `prep/photo-sound` 하나.** 단계마다 이 브랜치에 바로 커밋·push 한다(시작 전 `git pull --rebase`). main과 기존 앱 파일(`app.js`, `style.css`, `index.html`, `core.*`)은 준비 단계에서 **고치지 않는다.** 새 파일은 `docs/prep/`와 `lab/` 아래에만 만든다.
2. **사실만 적는다.** 조사 내용에는 출처 링크를 붙이고, 직접 확인하지 못한 것은 "확인 못 함"이라고 쓴다. 지금도 접속되는지 확인한 날짜를 적는다. 추측으로 표를 채우지 않는다.
3. **저작권.** 남의 사진·음원 샘플·코드를 가져오지 않는다. 시험용 그림은 코드로 그려서 만들고, 소리는 Web Audio 합성으로만 낸다. 라이브러리를 추천할 때는 라이선스를 적는다. 실제 브랜드의 화면·로고·이름을 흉내 내지 않는다.
4. **공모전 조건.** 로그인·결제 없이 체험, API 키가 필요한 서비스 금지, 외부 서비스가 죽어도 핵심 기능은 동작. 사진은 **기기 밖으로 보내지 않는 것**을 기본으로 한다(서버 업로드 없음).
5. **한국어**로 쓰고, 표와 짧은 문장 위주로 쓴다. 문서마다 맨 위에 "3줄 요약"과 "제작에 주는 결론"을 둔다.
6. 한 단계는 **50분 안**에 끝낸다. 다 못 하면 한 것까지 올리고 상태를 `일부`로 두고 남은 일을 적는다.
7. 단계를 시작할 때 아래 **진행 기록**의 상태를 `진행 중 (HH:MM KST)`로 바꿔 먼저 push 한다. 다른 실행이 70분 안에 `진행 중`으로 표시한 단계는 건너뛴다(겹침 방지).

### P1 사례 조사 — `01-prior-art.md`

- 찾을 것: 사진/이미지/색/그림 → 소리·음악 변환 서비스. 웹 서비스, 모바일 앱, 설치 작품, 연구·오픈소스를 모두 포함. 한국 서비스와 하입바이브(https://hypevibe.co.kr/services) 등록작 중 비슷한 것이 있는지도 확인.
- 출발점(직접 확인하고 더 찾을 것): Audible Color, Synesthesia(iOS), ROY G BIV, Synestizer, Chromatone, PIXELSYNTH, Photosounder, 이미지→스펙트로그램 소리 변환 도구, 구글 Arts & Culture의 그림·음악 실험, Imaginary Soundscape, AI 이미지→음악 생성 서비스.
- 표 항목: 이름 / 연도 / 종류(웹·앱·작품·연구) / 입력 / **변환 방식(무엇을 무엇에 대응시키는지)** / 출력 / 가격·로그인 / 지금 접속 가능 여부(확인 날짜) / 좋은 점 / 한계 / 출처.
- 정리: ① 변환 방식별 분류(색→음 대응, 스캔, 스펙트로그램, AI 생성 등) ② 사용자 반응이 좋았던 점·불만 ③ **우리 차별점 후보 5개** ④ 이름 후보("색의 노래" 포함 5개)와 같은 이름의 기존 서비스·상표가 있는지 검색 결과.

### P2 사진 분석 기법 — `02-image-analysis.md`

- 특징 후보마다: 무엇을 뽑는지 / 계산 방법 / 브라우저 구현(캔버스 픽셀, 필요 시 Web Worker) / 예상 속도(휴대폰 기준) / 음악의 무엇에 쓰기 좋은지.
  - 대표색 팔레트(중앙값 분할·k-평균·8진 트리 비교), 색 비율
  - 밝기·대비·채도 분포, 색온도(따뜻함/차가움)
  - 가장자리 밀도·질감(복잡한 사진 vs 단순한 사진)
  - 구도: 영역 나누기(위·가운데·아래, 3분할), 좌→우 흐름, 눈에 띄는 영역 근사
  - 얼굴·사물 인식(기기 안에서 도는 모델): 용량·속도·라이선스 비용을 따져 **넣을지 말지 판단**
- 입력 처리: 큰 사진 축소 기준, EXIF 회전, 투명 배경, 아주 어둡거나 단색인 사진 처리.
- 결론: MVP에 쓸 특징 묶음(필수/선택)과 분석 결과 **데이터 형식 초안**(JSON 예시).

### P3 소리 변환 기법 — `03-sonification.md`

- 음악 최소 규칙: 음계·조성, 화음 진행, 리듬 패턴, 15~30초 구성(도입–전개–마무리), 음색 합성(Web Audio만으로 내는 악기 4~6종 설계).
- 색–음 대응의 선행 사례(뉴턴, 스크리아빈, 칸딘스키 등): 사실관계를 출처와 함께 짧게. 과학적 근거가 아닌 것은 그렇다고 쓴다.
- 변환 방식 후보를 **같은 기준으로 비교**(듣기 좋음 / 사진과의 연결이 느껴짐 / 사진마다 달라짐 / 구현 난이도 / 설명하기 쉬움):
  - A. 팔레트 → 멜로디(지금 방식)
  - B. 좌→우 스캔 악보(사진을 악보처럼 읽기)
  - C. 영역별 레이어(하늘=패드, 가운데=멜로디, 아래=베이스 등)
  - D. 분위기 판정 → 조성·빠르기·악기 프리셋 + 사진 특징으로 변주
  - (조사 중 더 좋은 방식이 있으면 추가)
- 반드시 지킬 성질: **같은 사진 = 같은 노래**(결정적), 어떤 사진이어도 불협화음이 나지 않음, 서로 다른 사진은 듣고 구별될 만큼 다름.
- 결론: **추천안 1개 + 근거**, 특징→음악 대응표, 사용자에게 보여 줄 "왜 이런 소리가 났는지" 설명 문구 방식.

### P4 모바일·PC 호환성 — `04-compat.md`

- 대상: iOS Safari, 안드로이드 Chrome, 삼성 인터넷, **카카오톡·인스타그램 인앱 브라우저**(공유 링크가 여기서 열림), PC Chrome·Edge·Firefox·Safari.
- 항목별 지원 표 + 안 될 때 대체 경로:
  - 사진 넣기: 파일 선택, 바로 촬영, 끌어다 놓기, 붙여넣기(PC), HEIC 사진, 사진 방향(EXIF), 큰 사진 메모리 한도
  - 소리: 첫 재생 잠금 해제, iOS 무음 스위치, 백그라운드 전환 시 동작, OfflineAudioContext(파일로 굽기)
  - 내보내기·공유: WAV 저장, 영상(화면+소리) 녹화 형식(webm/mp4), 파일 공유(Web Share), 인앱 브라우저의 다운로드 제한, 링크 공유 시 미리보기
  - 화면: PC 2단·모바일 1단(지금 `core.js`의 View 구조), 가로·세로 전환, 터치·마우스·키보드
- 출처: MDN·caniuse·WebKit/Chromium 공식 문서 위주. 버전과 확인 날짜를 적는다.
- **실기기 점검표**: 클라우드에서는 실제 휴대폰을 못 쓰므로, 사람이 5분 안에 따라 할 수 있는 점검 순서(기기별)를 만든다.

### P5 시험 코드 — `lab/`

- `lab/analyze.js`: 픽셀 배열 → 특징(JSON). DOM에 기대지 않는 순수 함수(브라우저·node 양쪽에서 동작).
- `lab/compose.js`: 특징 → 음표 이벤트 목록(시각·음높이·길이·세기·악기). 결정적. P3의 후보 방식 중 상위 2~3개를 각각 구현.
- `lab/render.js`: 음표 이벤트 → Web Audio 재생, OfflineAudioContext로 WAV 만들기.
- `lab/index.html`: 사진을 넣고(끌어다 놓기·파일 선택) 방식별로 **번갈아 들어 보는** 비교 페이지. 분석 결과(팔레트·특징 값)와 "왜 이런 소리인지"를 같이 보여 준다. PC·모바일 모두 동작.
- `lab/samples/`: 코드로 그린 시험 그림 12장 이상(단색, 그라데이션, 노을 느낌, 숲 느낌, 야경 느낌, 흑백, 아주 복잡한 무늬 등) + 만드는 스크립트.
- `lab/test/`: node로 도는 테스트 — 결정성(같은 입력 2번 = 같은 결과), 음계 밖 음 없음, 길이 15~30초, 서로 다른 그림의 결과가 충분히 다름(차이 지표 정의), 극단 입력(1×1, 단색, 4000×3000)에서 오류 없음, 분석 시간 측정.
- 브라우저 확인: workspace `qa/launch.js`(헤드리스 브라우저)로 `lab/index.html`을 PC 1280px·모바일 390px에서 열어 오류·가로 넘침이 없는지 확인하고, 테스트를 `lab/test/`에 남긴다.
