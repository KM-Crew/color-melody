# P2 사진 분석 기법 — 브라우저에서 사진으로부터 뽑을 수 있는 것 (2026-11-24)

## 3줄 요약

1. 음악에 쓸 만한 특징(대표색·밝기·대비·채도·따뜻함·복잡함·구도)은 **전부 캔버스 픽셀만으로**, 외부 라이브러리 없이 계산된다. 긴 변 128픽셀로 줄인 사진 기준 node 실측 **합계 약 2ms**(4절). Web Worker는 필요 없다.
2. **분석 크기를 하나로 고정**해야 한다(긴 변 128). 가장자리 밀도는 분석 크기에 따라 값이 2배 이상 달라졌다(실측). 크기를 고정하지 않으면 "같은 사진 = 같은 노래"가 깨진다.
3. **얼굴·사물 인식은 MVP에 넣지 않는다.** 얼굴 모델 자체는 230KB지만 실행기(wasm)가 14.7MB(gzip 4.1MB)이고, 외부 CDN 의존·첫 실행 지연이 생긴다. 대신 "눈에 띄는 곳"을 색 차이로 근사한다.

## 제작에 주는 결론

- **입력 처리 순서(고정):** 파일 → `<img>` 로 디코드 → 긴 변 128 캔버스에 `drawImage`(여기서 EXIF 회전이 적용됨) → `getImageData` → 분석. **(P5에서 바뀜: 긴 변 512 → 128 두 번에 줄인다. 1단계와 멜로디 1칸 차이가 실측됨 — [lab/README](../../lab/README.md), [BUILD_SPEC](BUILD_SPEC.md) 4-1절)** 화면에 보여 줄 그림은 따로 긴 변 1280 이하로 그린다. 원본 크기 캔버스는 만들지 않는다(iOS 메모리 한도, 5절).
- **팔레트는 지금 `app.js`의 "칸 묶기" 방식을 유지**하고 비율(`share`)을 추가한다. 중앙값 분할·k-평균보다 50~75배 빠르고(실측), "선명한 색을 우선"하는 점이 음악용으로 맞다. 단 색 수가 5개보다 적게 나올 수 있으므로 작곡 쪽이 1~5색을 모두 받아야 한다.
- **필수 특징 7묶음:** 팔레트+비율 / 밝기 / 대비 / 채도 / 따뜻함 / 가장자리 밀도 / 세로줄 16개 스캔. **선택:** 3×3 칸 평균, 눈에 띄는 곳, 색 풍부함, 회색조 여부(7절).
- **분석 결과는 숫자를 반올림해서** 내보낸다(소수 3자리). 브라우저마다 축소 결과가 조금 달라도 같은 음악이 나오게 하려면 작곡 단계에서 값을 **구간으로 나눠** 쓴다(예: 밝기 5단계). → P3·P5에 넘김.
- **흑백·단색·아주 어두운 사진**은 오류가 아니라 정상 입력이다. 각각에 대한 기본값을 5절에 정했다. P5 테스트에 그대로 넣는다.
- 특징 → 음악 대응은 P3의 일이다. 이 문서의 "쓰기 좋은 곳" 칸은 후보일 뿐이다.

## 1. 특징 후보 표

"속도"는 긴 변 128(=16,384픽셀) 기준 node 실측값이다(4절). 휴대폰 값은 재지 못했다(추정은 4-3).

| # | 특징 | 무엇을 뽑는지 | 계산 방법 | 브라우저 구현 | 속도(128px, node) | 음악에서 쓰기 좋은 곳(후보) |
|---|---|---|---|---|---|---|
| 1 | **대표색 팔레트 + 비율** | 사진을 대표하는 색 1~5개와 각 색이 차지하는 넓이 비율 | 2절 비교 참고. 추천: 4비트 칸 묶기 + 서로 먼 색 고르기 | 픽셀 한 번 훑기. 라이브러리 없음 | 0.16ms | 음계 안의 주요 음 고르기, 악기 고르기, 결과 화면의 색 띠 |
| 2 | **밝기** | 평균 밝기(0~1), 어두운 쪽 5%·밝은 쪽 95% 지점 | 밝기 = 0.2126R + 0.7152G + 0.0722B 의 평균과 256칸 히스토그램 | 같은 훑기에서 함께 계산 | 3~7 합쳐 0.17ms | 음역(옥타브), 장조/단조 느낌 |
| 3 | **대비** | 밝기의 표준편차, (95% − 5%) 폭 | 위 히스토그램에서 | 〃 | 〃 | 셈여림 폭, 음 사이 간격 |
| 4 | **채도** | 평균 채도(0~1) | 픽셀마다 (최대−최소)/최대 의 평균 | 〃 | 〃 | 음색의 밝기(필터), 세기 |
| 5 | **따뜻함** | 붉은 쪽인지 푸른 쪽인지(−1~1) | (R − B)/255 의 평균. 물리적인 색온도(K)가 아니라 **단순 지표** | 〃 | 〃 | 악기 계열, 조성 |
| 6 | **색 풍부함** | 여러 색이 얼마나 다채롭게 섞였는지 | Hasler·Süsstrunk(2003) 식: rg = R−G, yb = (R+G)/2−B 의 표준편차와 평균 조합 | 〃 | 〃 | 성부 수, 화음의 풍성함 |
| 7 | **회색조 여부** | 흑백 사진인지 | 평균 채도 < 0.08 이면 참(기준값은 P5에서 시험 그림으로 조정) | 〃 | 〃 | 흑백 전용 음색·음계로 분기 |
| 8 | **가장자리 밀도** | 사진이 복잡한지 단순한지(0~1) | 밝기 그림에 소벨 3×3, 세기가 기준 넘는 픽셀의 비율 | 픽셀 한 번 더 훑기 | 0.72ms | 음표 개수(리듬 밀도), 빠르기 |
| 9 | **세로줄 스캔** | 왼쪽→오른쪽 16칸 각각의 평균색·밝기·"밝은 부분이 위쪽에 있는 정도" | 가로를 16등분해서 칸마다 평균 | 한 번 훑기 | 9~11 합쳐 0.77ms | 멜로디 윤곽(시간 순서), 재생 막대와 연결 |
| 10 | **3×3 칸 평균** | 위·가운데·아래 × 왼·가운데·오른 9칸의 평균색 | 칸마다 평균 | 〃 | 〃 | 영역별 성부(위=높은 성부, 아래=베이스) |
| 11 | **눈에 띄는 곳** | 시선이 갈 만한 위치(x, y 0~1) | 전체 평균색과의 차이를 무게로 한 무게중심(근사) | 〃 | 〃 | 곡의 절정 위치, 스테레오 좌우 |
| 12 | 얼굴·사물 | 얼굴 수·위치, 사물 종류 | 기기 안 모델(3절) | wasm + 모델 내려받기 | 측정 안 함 | (넣지 않음) |

근거와 주의:

- 밝기 계수 0.2126/0.7152/0.0722 는 Rec. 709 휘도 계수다. 엄밀히는 감마를 푼 선형 값에 써야 하지만, 여기서는 사진끼리 비교하는 지표라 sRGB 값에 그대로 쓴다(단순화).
- **따뜻함은 색온도가 아니다.** 실제 상관색온도는 xy 색도에서 McCamy(1992) 근사식으로 구하지만([colour 라이브러리 구현](https://colour.readthedocs.io/en/latest/_modules/colour/temperature/mccamy1992.html)), 그건 광원을 재는 식이고 사진 전체의 "분위기"를 재는 데는 맞지 않는다. R−B 평균이면 충분하고 한 문장으로 설명된다.
- 색 풍부함 식은 2차 자료(구현 예: [PyImageSearch](https://pyimagesearch.com/2017/06/05/computing-image-colorfulness-with-opencv-and-python/))에서 확인했다. 논문 원문([EPFL](https://infoscience.epfl.ch/record/33994?ln=en))은 초록만 확인. 구현마다 절댓값을 취하는지가 다르다 → 우리는 원문 정의(절댓값 없음)로 쓰고 "참고 지표"로만 둔다.
- 밝기·채도와 감정의 관계는 색 조각 실험 결과가 있다(Valdez·Mehrabian 1994: 즐거움 = 0.69×밝기 + 0.22×채도, 각성 = −0.31×밝기 + 0.60×채도. [PubMed](https://pubmed.ncbi.nlm.nih.gov/7996122/)). **단색 조각 실험이지 사진 실험이 아니다.** "밝고 선명하면 밝은 곡" 정도의 방향 근거로만 쓰고, 과학적으로 증명된 대응이라고 쓰지 않는다. → P3에서 다룸.
- "눈에 띄는 곳"의 정식 기법으로 스펙트럼 잔차법(Hou·Zhang, CVPR 2007: 로그 진폭 스펙트럼에서 평균을 뺀 나머지를 역변환. [논문 정보](https://mlanthology.org/cvpr/2007/hou2007cvpr-saliency))이 있다. FFT가 필요하고, 잔차 자체는 큰 의미가 없다는 반론도 있다([BMVC 2011](https://www.bmva-archive.org.uk/bmvc/2011/proceedings/paper86/paper86.pdf)). MVP에는 "평균색과 다른 곳"이라는 근사로 충분하다(설명도 쉽다).

## 2. 대표색 뽑기 3종 비교

같은 시험 그림(코드로 생성, 128×128, 5색)으로 직접 구현해 쟀다. 품질은 "각 픽셀을 가장 가까운 팔레트 색으로 바꿨을 때의 평균 제곱 오차"(낮을수록 사진을 고르게 대표).

| 방식 | 원리 | 시간(128px) | 오차: 풍경 느낌 / 노을 / 잡음 | 결정적인가 | 특징 |
|---|---|---|---|---|---|
| **칸 묶기 + 먼 색 고르기** (지금 `app.js`) | RGB를 4비트씩(4096칸)으로 묶고, 많이 나온·선명한 칸부터 서로 충분히 다른 색만 고름 | **0.16ms** | 606 / 250(4색) / 4190 | 예 | 가장 빠름. 선명한 색을 일부러 우선해서 오차는 큰 편. 색이 5개보다 적게 나올 수 있음 |
| 중앙값 분할 | 가장 넓게 퍼진 색 축을 가운데서 자르기를 반복 | 8.3ms | 705 / 180 / 2262 | 예(정렬 동점 처리를 고정하면) | 넓은 면적 색 위주. 작지만 눈에 띄는 색(꽃 한 송이)을 놓치기 쉬움 |
| k-평균(8회 반복) | 중심점을 옮겨 가며 묶기. 시작점은 중앙값 분할 결과 | 12.1ms | **455 / 163 / 2197** | 시작점을 고정하면 예(무작위 시작이면 아니오) | 오차가 가장 작음. 가장 느림 |
| 8진 트리 | 색 공간을 8갈래 나무로 쪼갠 뒤 잎을 합침 | 구현·측정 안 함 | — | 예 | 문헌상 중앙값 분할과 결과가 비슷하고 속도·메모리가 유리하다고 함([Ozturk 외, Informatica](https://informatica.vu.lt/journal/INFORMATICA/article/737/file/pdf)). 직접 비교는 안 함 |

- 문헌: k-평균은 시작점을 잘 잡고 구현을 다듬으면 품질·속도 모두 경쟁력이 있다([Celebi 2011, arXiv:1101.0395](https://ar5iv.labs.arxiv.org/html/1101.0395)). 세 방식을 한 번에 견준 공인 벤치마크는 찾지 못했다.
- **판단:** 우리 목적은 "사진을 압축"이 아니라 "사람 눈에 띄는 색 몇 개"다. 오차가 낮은 것보다 **선명한 색을 놓치지 않는 것**이 중요하고, 12ms도 충분히 빠르지만 굳이 바꿀 이유가 없다. → **칸 묶기 유지 + 비율 추가.** 품질이 아쉬우면 P5에서 "칸 묶기로 고른 색을 시작점으로 k-평균 2~3회"를 시험해 볼 수 있다(선택).
- 색 사이 거리를 지금은 RGB 직선거리로 잰다. 사람 눈에 더 맞는 Oklab 거리로 바꾸는 방법이 있다(행렬 2번 + 세제곱근. 원 구현은 퍼블릭 도메인이라고 2차 자료에 나옴: [Wikipedia](https://en.wikipedia.org/wiki/Oklab_color_space). 원문 라이선스 문구는 확인 못 함). **MVP에는 불필요**, 색이 비슷하게 뽑힌다는 불만이 나오면 검토.
- 기존 라이브러리(쓰지 않음, 참고용. npm 레지스트리에서 2026-11-24 확인): `colorthief` 3.5.0 MIT, `quantize` 1.0.2 MIT(중앙값 분할), `node-vibrant` 4.0.4 MIT. 직접 구현이 40줄 안쪽이라 가져올 필요가 없다.

## 3. 얼굴·사물 인식 — 넣지 않는다

| 후보 | 라이선스 | 용량(직접 확인) | 비고 |
|---|---|---|---|
| MediaPipe Face Detector(`@mediapipe/tasks-vision` 1.2.3) + BlazeFace short-range 모델 | Apache-2.0(npm 표기) | 모델 229,746바이트. **실행기 wasm 14,665,716바이트(gzip 약 4.1MB)** + JS 약 34만 바이트 | 공식 안내는 wasm을 CDN에서 받게 되어 있음([구글 문서](https://developers.google.com/edge/mediapipe/solutions/vision/face_detector)). 모델 파일 자체의 라이선스 문구는 확인 못 함 |
| MediaPipe Object Detector + EfficientDet-Lite0 | 〃 | 모델 7,254,339바이트 + 위 실행기 | 사물 80종 |
| MediaPipe Image Classifier + EfficientNet-Lite0 | 〃 | 모델 18,582,189바이트 + 위 실행기 | 1000종 분류 |
| TensorFlow.js + coco-ssd 2.2.3 | Apache-2.0 | tfjs 묶음 크기는 확인 못 함(npm 풀린 크기 147MB는 소스 포함이라 참고 불가) | 2023-11 이후 갱신 없음 |
| face-api.js 0.22.2 | MIT | 풀린 크기 4.9MB | 2022-05 이후 갱신 없음 |
| 브라우저 내장 `FaceDetector`(Shape Detection API) | — | 0 | 크롬에서 실험 기능 플래그 뒤에 있고 기기마다 지원이 다름([Chrome 문서](https://developer.chrome.com/docs/capabilities/shape-detection)). Safari·Firefox 지원은 확인 못 함. **쓸 수 없음** |

넣지 않는 이유:

1. **용량·지연:** 얼굴만 해도 첫 실행에 4MB 이상을 더 받아야 한다. 30초 체험에서 "사진 넣고 바로 소리"가 늦어진다.
2. **외부 의존:** CDN을 쓰면 "외부 서비스가 죽어도 핵심 기능 동작" 조건에 걸리고, 직접 올리면 저장소에 15MB 이진 파일이 들어간다.
3. **설명하기 어려움:** "얼굴이 있어서 이런 소리"는 틀렸을 때(오인식) 어색하고, 인물 사진을 분석한다는 인상이 "사진을 보내지 않는다"는 신뢰 문구와 충돌할 수 있다.
4. **대체 가능:** "눈에 띄는 곳"(1절 11번)으로 절정 위치 정도는 정할 수 있다.

나중에 넣는다면: 결과 화면이 먼저 뜬 뒤 **선택 기능으로 늦게 불러오기**, 실패해도 음악은 그대로.

## 4. 속도 실측

### 4-1. 크기별 시간 (node v22, Xeon 2.1GHz, 1회 평균 ms)

| 분석 크기 | 칸 묶기 | 중앙값 분할 | k-평균 | 통계(2~7) | 소벨(8) | 구도(9~11) | **합계(칸 묶기 기준)** |
|---|---|---|---|---|---|---|---|
| 64×64 | 0.22 | 1.58 | 3.00 | 0.18 | 0.29 | 0.46 | 1.15 |
| 96×96 | 0.13 | 4.21 | 6.27 | 0.09 | 0.43 | 0.52 | 1.18 |
| **128×128** | 0.16 | 8.33 | 12.08 | 0.17 | 0.72 | 0.77 | **1.83** |
| 192×192 | 0.26 | 18.55 | 27.47 | 0.49 | 2.23 | 2.32 | 5.30 |
| 256×256 | 0.38 | 31.41 | 48.64 | 0.86 | 4.35 | 3.48 | 9.08 |

(64×64 값이 96×96보다 큰 칸은 첫 실행 예열 영향이다. 경향만 볼 것.)

### 4-2. 분석 크기에 따라 값이 달라지는가

같은 규칙으로 만든 그림을 크기만 바꿔 쟀다.

| 크기 | 밝기 | 대비 | 채도 | 따뜻함 | 색 풍부함 | **가장자리 밀도** |
|---|---|---|---|---|---|---|
| 64 | 0.485 | 0.138 | 0.495 | −0.016 | 104.7 | **0.111** |
| 128 | 0.484 | 0.139 | 0.496 | −0.013 | 104.9 | **0.049** |
| 256 | 0.483 | 0.139 | 0.497 | −0.012 | 105.0 | **0.024** |

- 밝기·대비·채도·따뜻함은 크기와 거의 무관하다.
- **가장자리 밀도는 크기에 크게 좌우된다.** → 분석 크기를 **긴 변 128로 고정**하고, 기준값도 그 크기에서 정한다.
- 한계: 이 시험은 "큰 그림을 줄인 것"이 아니라 "크기별로 새로 그린 것"이다(픽셀 잡음이 크기마다 같은 세기로 들어감). 실제 사진을 브라우저가 줄일 때는 잡음이 뭉개져서 차이가 더 작을 수 있다. 브라우저 축소 결과로는 재지 못했다 → P5 브라우저 확인에서 다시 잴 것.

### 4-3. 휴대폰에서는? (추정, 실측 아님)

- 실기기로 재지 못했다. 다만 합계가 2ms 수준이라 휴대폰이 이 서버보다 10배 느리다고 가정해도 20ms 안쪽이다. **분석 계산은 병목이 아니다.**
- 실제로 시간이 걸리는 곳은 계산이 아니라 **큰 사진 디코드와 축소**(4000×3000 JPEG를 여는 일)다. 이 시간은 재지 못했다. → P5에서 헤드리스 브라우저로 4000×3000 그림을 넣어 재고, P4 실기기 점검표에 "사진 선택 후 소리가 날 때까지 걸린 시간" 항목을 넣을 것.
- Web Worker: 계산이 가벼워서 **쓰지 않는다.** 워커 안에서 캔버스를 쓰려면 `OffscreenCanvas`가 필요한데 Safari는 16.4부터 2D만 지원한다([web.dev](https://web.dev/articles/offscreen-canvas)). 구형 기기 대응 코드를 늘릴 이유가 없다.

## 5. 입력 처리

| 상황 | 처리 | 근거·확인 상태 |
|---|---|---|
| **큰 사진** | 분석용: 긴 변 128로 `drawImage`(P5에서 512 → 128 2단계로 확정, 아래 줄). 표시용: 긴 변 1280 이하. 원본 크기 캔버스는 만들지 않음 | iOS Safari 캔버스는 넓이 16,777,216픽셀(=4096×4096) 한도와 전체 캔버스 메모리 한도(보고된 값 224~384MB, 버전·기기마다 다름)가 따로 있다([pqina 1](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/), [pqina 2](https://www.pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/)). 2024년에 한도를 8192×8192로 올리는 WebKit 변경이 처리됐으나 적용 버전은 확인 못 함([WebKit 271002](https://bugs.webkit.org/show_bug.cgi?id=271002)). 4000×3000(1200만 픽셀)은 한도 안이지만 `<img>` 디코드 자체가 메모리를 쓴다 |
| 한 번에 크게 줄일 때 품질 | 4000→128처럼 30배 줄이면 브라우저 보간 방식에 따라 잡음이 남을 수 있다. 대책: 먼저 긴 변 512로 줄이고 다시 128로(2단계) | 브라우저별 차이는 확인 못 함. P5에서 1단계/2단계 결과를 비교해 정할 것 |
| **EXIF 회전**(세로로 찍은 사진) | 별도 코드 없이 `<img>` → `drawImage` 로 처리. EXIF 파서 라이브러리를 넣지 않는다 | CSS `image-orientation` 기본값이 `from-image`이고 2020년 4월 이후 주요 브라우저 공통([MDN](https://developer.mozilla.org/docs/Web/CSS/image-orientation), 검색 요약 기준). 크롬 81·사파리 13.1에서 캔버스에도 적용된다는 표가 CSS 작업 그룹 메일에 있다([W3C 메일](https://lists.w3.org/Archives/Public/public-css-archive/2020Apr/0170.html)). 파이어폭스 적용 버전은 확인 못 함. **주의:** 그림·캔버스가 문서에 붙어 있지 않을 때 브라우저마다 결과가 다를 수 있다는 보고가 있다([W3C 메일](https://lists.w3.org/Archives/Public/public-css-archive/2020Jan/0244.html)) → P4 실기기 점검표에 "세로 사진이 누워 보이지 않는지" 항목 |
| `createImageBitmap` 로 디코드+축소 | **쓰지 않는다**(`<img>` 경로 하나로 통일) | 회전 옵션 이름이 `none`→`from-image`로 바뀐 이력이 있고 Safari 지원이 불분명하다([caniuse](https://caniuse.com/mdn-api_createimagebitmap_options_imageorientation_parameter_from-image), [WebKit 250476](https://bugs.webkit.org/show_bug.cgi?id=250476)). 확인 못 함 |
| **투명 배경**(PNG) | 알파 < 128 인 픽셀은 계산에서 뺀다(지금 `app.js`와 같음). 남는 픽셀이 전체의 2% 미만이면 "거의 빈 사진"으로 보고 흰 배경에 합성해 다시 계산 | 직접 정한 규칙. P5에서 시험 |
| **단색 사진** | 팔레트 1색, 대비 0, 가장자리 0 으로 정상 처리(벤치에서 오류 없음 확인). 작곡 쪽이 "한 음 중심의 조용한 곡"으로 받는다 | `lab/bench/p2-bench.js` 극단 입력 |
| **아주 어두운 사진**(야경) | 그대로 분석하되, 팔레트에서 검정을 덜 뽑는 지금 규칙 유지. 밝기 95% 지점이 0.15 미만이면 `flags.veryDark` 를 켠다 | 직접 정한 규칙(기준값은 P5에서 조정) |
| **흑백 사진** | `flags.grayscale` 을 켠다. 색상으로 음을 정할 수 없으므로 작곡 쪽이 밝기만으로 음을 고른다 | 지금 `app.js`의 `gray: s < .12` 와 같은 생각 |
| **1×1, 2×2 등 아주 작은 그림** | 소벨은 3×3이 안 되면 0을 돌려준다. 세로줄 16칸은 빈 칸이 생기면 가장 가까운 칸 값으로 채운다 | 벤치에서 1×1·2×2·128×2 오류 없음 확인(빈 칸 채우기는 P5에서 구현) |
| **극단적으로 길쭉한 사진**(파노라마, 긴 캡처) | 긴 변 128 기준이면 짧은 변이 몇 픽셀이 될 수 있다 → 짧은 변 최소 16픽셀을 보장(그때는 긴 변이 128을 넘는 것을 허용, 최대 512) | 직접 정한 규칙 |
| HEIC·열 수 없는 파일 | `img.onerror` → "사진을 열 수 없어요" 안내(지금과 같음). 형식별 지원은 P4에서 | P4로 넘김 |
| `getImageData` 를 여러 번 부를 때 | 캔버스 컨텍스트를 `{ willReadFrequently: true }` 로 만든다(지금 `app.js`도 그렇게 함). 분석은 1번만 읽으므로 영향은 작다 | 속도 차이는 재지 못함 |

**같은 사진 = 같은 노래에 대한 주의.** 분석 함수 자체는 결정적이지만, **브라우저가 사진을 줄이는 방식(보간)은 브라우저마다 다를 수 있다.** 그래서 같은 사진이라도 기기에 따라 픽셀 값이 조금 다를 수 있다(실제 차이 크기는 확인 못 함). 대책 두 가지를 같이 쓴다.

1. 작곡 단계에서 특징 값을 **구간으로 나눠** 쓴다(밝기 0.484와 0.487이 같은 결과가 되게).
2. 공유 링크에는 사진이 아니라 **분석 결과(또는 거기서 나온 곡 씨앗)** 를 담는다. 받는 사람은 다시 분석하지 않으므로 보낸 사람과 완전히 같은 곡을 듣는다. 사진도 기기 밖으로 나가지 않는다.

## 6. 분석 결과 데이터 형식 초안

P5 `lab/analyze.js` 가 돌려줄 모양. 숫자는 예시다(실제 사진의 값이 아님).

```json
{
  "v": 1,
  "size": { "w": 128, "h": 96, "pixels": 12288 },
  "palette": [
    { "hex": "#e8743b", "share": 0.31, "h": 20, "s": 0.79, "l": 0.57 },
    { "hex": "#2b3a67", "share": 0.27, "h": 225, "s": 0.41, "l": 0.29 },
    { "hex": "#f4d58d", "share": 0.18, "h": 42, "s": 0.82, "l": 0.75 },
    { "hex": "#7a4b3a", "share": 0.14, "h": 16, "s": 0.36, "l": 0.35 },
    { "hex": "#c9cfd6", "share": 0.10, "h": 212, "s": 0.14, "l": 0.81 }
  ],
  "tone": {
    "brightness": 0.52, "p5": 0.11, "p95": 0.89, "contrast": 0.24,
    "saturation": 0.48, "warmth": 0.21, "colorfulness": 61.3
  },
  "texture": { "edgeDensity": 0.083, "edgeMean": 0.047 },
  "layout": {
    "columns": [
      { "hex": "#d9743f", "l": 0.55, "s": 0.66, "lift": 0.62 }
    ],
    "grid": ["#f0b27a", "#f4d58d", "#e8a15c", "#b0653f", "#e8743b", "#8e5a45", "#2b3a67", "#34406b", "#27304f"],
    "focus": { "x": 0.61, "y": 0.44 }
  },
  "flags": { "grayscale": false, "veryDark": false, "flat": false, "mostlyTransparent": false }
}
```

| 필드 | 뜻 | 범위 | 필수 |
|---|---|---|---|
| `v` | 형식 버전. 공유 링크에 들어가므로 바꿀 때 올린다 | 정수 | 필수 |
| `size` | 분석에 쓴 크기와 실제로 센 픽셀 수(투명 제외) | — | 필수 |
| `palette[]` | 대표색 1~5개, 비율 큰 순. `share` 합은 1(가장 가까운 대표색에 픽셀을 나눠 센 비율) | h 0~359, s·l·share 0~1 | 필수 |
| `tone.brightness` / `p5` / `p95` | 평균 밝기, 어두운 5%·밝은 95% 지점 | 0~1 | 필수 |
| `tone.contrast` | 밝기 표준편차 | 0~약 0.5 | 필수 |
| `tone.saturation` | 평균 채도 | 0~1 | 필수 |
| `tone.warmth` | 붉은 쪽(+)·푸른 쪽(−) | −1~1 | 필수 |
| `tone.colorfulness` | 색 풍부함(참고 지표) | 0~약 200 | 선택 |
| `texture.edgeDensity` | 가장자리 픽셀 비율(긴 변 128 기준) | 0~1 | 필수 |
| `texture.edgeMean` | 가장자리 세기 평균 | 0~1 | 선택 |
| `layout.columns[16]` | 왼→오 16칸의 평균색·밝기·채도·`lift`(밝은 부분이 위쪽일수록 큼) | 0~1 | 필수 |
| `layout.grid[9]` | 3×3 칸 평균색(왼쪽 위부터 가로로) | — | 선택 |
| `layout.focus` | 눈에 띄는 곳 | 0~1 | 선택 |
| `flags` | 특수한 사진 표시. `flat` = 단색(대비 < 0.02 이고 가장자리 0) | 참/거짓 | 필수 |

규칙:

- 모든 소수는 **3자리 반올림**(벤치에서 단색 그림의 대비가 0이 아니라 1.3e-7 로 나왔다 — 반올림하지 않으면 이런 값이 분기를 흔든다).
- 팔레트 순서는 비율 큰 순, 비율이 같으면 색상(h) 작은 순 → 결정적.
- 팔레트가 0개인 경우(전부 투명)는 `mostlyTransparent` 처리 후 다시 계산하므로 결과에는 항상 1개 이상.
- 공유 링크에 다 넣기엔 크다(특히 `columns`). 링크용 축약 형식은 P3에서 작곡에 실제로 쓰는 값이 정해진 뒤 P6에서 정한다. → **정해짐:** 특징이 아니라 곡 설정값을 51~79자 글자열로 담는다(`lab/seedlink.js`, [BUILD_SPEC](BUILD_SPEC.md) 5-3절).

| 구분 | 특징 | 이유 |
|---|---|---|
| **필수** | 팔레트 + 비율 | 지금 앱의 핵심이고 결과 화면에 그대로 보여 줄 수 있음 |

| **필수** | 세로줄 16칸 스캔 | P1 결론("왼쪽→오른쪽으로 읽는다"는 설명·재생 막대)에 필요 |

| 선택 | 눈에 띄는 곳 | 절정 위치·스테레오. 근사라서 틀릴 수 있음 |
| 선택 | 색 풍부함 | 채도·팔레트 수와 겹침. 구별력이 있는지 P5에서 보고 결정 |
| 제외 | 얼굴·사물 인식 | 3절 |
| 제외 | 스펙트럼 잔차 시선 지도, Oklab 거리 | 효과 대비 구현·설명 비용이 큼 |
